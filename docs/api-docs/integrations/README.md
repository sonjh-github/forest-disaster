# 산림재난 장비·AI 연동 API 문서

이 문서군은 컨소시엄 참여기업·기관이 실제 endpoint와 원시 payload를 확정하기 전에 통합팀이 먼저 배포할 최소 계약을 정의한 결과다. 포트폴리오 관점의 핵심은 장비 기능을 구현했다는 주장이 아니라, 주관기관 관점에서 문서 근거와 통합 설계값을 분리하고 참여기관별 책임과 교체 가능한 어댑터 경계를 관리한 것이다.

## 문서 목적

산불·산사태 연구개발계획서와 2025년도 연차보고서의 본문, 표, 회로/구성도,
데이터 흐름 그림을 근거로 통합시스템이 장비 및 AI 서비스와 주고받을 API를 정의한다.

본 문서는 참여기업의 제조사 원본 프로토콜을 대신하지 않는다. 과제 문서가 기능과 데이터 항목을
명시하더라도 JSON 키, HTTP 경로, UUID 사용 여부까지 정하지 않은 경우가 많으므로
모든 항목을 다음 세 등급으로 구분한다.

| 등급 | 코드 | 의미 |
|---|---|---|
| 확인됨 | `CONFIRMED` | 연구계획서 또는 연차보고서 본문·표·그림에 기능이나 데이터가 직접 명시됨 |
| 추정 | `INFERRED` | 문서에 명시된 기능을 구현하려면 필요하다고 합리적으로 도출되지만 필드 자체는 직접 명시되지 않음 |
| 임의 정의 | `DESIGNED` | HTTP/JSON 통합을 위해 본 시스템이 정한 키, 코드, 기본값, 타임아웃, 식별 방식 |

`CONFIRMED`는 장비의 실제 출력 포맷이 확정되었다는 뜻이 아니다. 예를 들어 문서가
`RSSI 수집 및 LTE 전송`을 명시하면 RSSI 데이터의 존재는 확인됨이지만,
JSON 키 `rssiDbm`과 단위 dBm은 통합 계약으로 임의 정의한 것이다.

## 공통 전송 봉투

```json
{
  "context": {
    "eventId": "10000000-0000-4000-8000-000000000001",
    "requestId": "274e2c46-8fa8-4b01-bad7-623a62c91146",
    "sourceSystem": "rtk-terminal",
    "occurredAt": "2026-07-23T06:49:22.405Z",
    "schemaVersion": "1.0"
  },
  "data": {}
}
```

공통 봉투의 모든 키와 UUID·ISO 8601·버전 `1.0`은 `DESIGNED`다.
사건·시간·출처를 연결해야 한다는 필요성은 통합시스템 구현상 `INFERRED`다.

## 현재 구현과 문서 계약의 관계

- 현재 Hono API: `/api/v1/integrations/{capabilityId}/invoke`, `/results`
- 현재 전송 제한시간: 모사서버 5초 (`DESIGNED`)
- 실제 장비 URL·보안 헤더·서명: 미확정
- 실제 장비 원본 JSON은 기능별 어댑터가 이 문서의 표준 JSON으로 변환
- 프론트와 모사서버는 Supabase에 직접 접근하지 않고 백엔드를 경유

## 사용 원칙

1. `CONFIRMED` 항목은 삭제하거나 의미를 변경하지 않는다.
2. `INFERRED` 항목은 장비·모델 담당자와 협의 후 `CONFIRMED` 또는 `DESIGNED`로 재분류한다.
3. `DESIGNED` 항목은 참여기업·기관 프로토콜에 맞춰 어댑터 내부에서 변환할 수 있다.
4. 문서에 없는 임계값·정확도·커버리지 퍼센트를 과제 목표값으로 표현하지 않는다.
5. AI 결과는 추정치이며 운영자 승인 전 확정 판단이나 자동 명령으로 취급하지 않는다.

## 현재 증거와 남은 입력

- 구현 증거: 26개 capability 레지스트리, 공통 envelope 검증, 모사 픽스처와 장애모드 테스트
- 참여기업·기관에서 회신할 입력: 실제 URL, 인증·서명, 원시 JSON/바이너리 명세, 오류코드, 장비 ID, 현장 KPI 산식
- 미검증: 실제 RF 장비, 제조사 NMS, 외부 AI 추론, 처리성능과 장애복구

따라서 `CONTRACT_ONLY` 기능은 “연동 규격 준비”로 표현하고 “연동 완료”로 표현하지 않는다.

## 배포·회수 절차

1. 통합팀이 기능 ID, envelope, 필수 필드와 오류 형식을 포함한 버전 문서를 배포한다.
2. 담당 참여기업·기관은 실제 endpoint·인증·원시 필드·오류코드를 회신한다.
3. 통합팀은 확인된 값과 설계값을 구분해 규격과 provenance를 갱신한다.
4. 양측이 동일 request/response fixture로 계약시험을 수행한다.
5. 결과를 API 메시지 원장과 실증 증적에 연결한 뒤 해당 버전을 기준선으로 관리한다.
